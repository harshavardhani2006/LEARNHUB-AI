# Module 05: Chat History Module

> **Persistent conversation storage, retrieval, search, and continuation**

---

## 1. Module Overview

The Chat History Module ensures that every interaction between a user and the AI Tutor is **saved, searchable, and resumable**. Users can view previous conversations, continue old discussions, and search through their chat history — creating a continuous personalized learning experience.

### 1.1 Module Goals

- Persist every AI conversation and message to the database
- Allow users to browse and search previous chats
- Enable seamless continuation of old discussions with full context
- Auto-generate meaningful conversation titles
- Load complete message history when reopening a chat
- Support conversation management (delete, rename)

### 1.2 Dependencies

| Module | Relationship |
|--------|-------------|
| Module 02 – Authentication | Chat history requires verified authenticated user |
| Module 04 – RAG AI Assistant | Messages generated by AI Tutor are stored here |
| Module 09 – Database Design | `conversations` and `messages` tables |

## 3. Conversation Lifecycle

### 3.1 Creating a New Conversation

```text
User clicks "New Chat" or "Ask AI" on a resource
        ↓
POST /conversations → New row in conversations table
        ↓
Conversation ID returned to frontend
        ↓
User sends first message
        ↓
POST /chat with conversation_id
        ↓
User message saved to messages table
        ↓
AI response generated and saved to messages table
        ↓
Conversation title auto-generated from first user message
        ↓
Title updated in conversations table
```

### 3.2 Continuing an Existing Conversation

```text
User clicks on a previous chat in sidebar/list
        ↓
GET /messages/{conversation_id}
        ↓
All messages loaded and displayed in chat UI
        ↓
User sends new message
        ↓
POST /chat with conversation_id + full history as context
        ↓
New messages appended to existing conversation
```

### 3.3 Auto-Generated Titles

| Rule | Detail |
|------|--------|
| **Source** | First user message in the conversation |
| **Format** | Truncated to 50 characters |
| **Example** | User asks "Explain normalization in simple words" → Title: "Explain normalization in simple words" |
| **Fallback** | If first message is too short, use "New Conversation" |
| **Editable** | User can rename later (optional feature) |

## 5. Message Storage

### 5.1 Message Structure

Each message in a conversation is stored with:

| Field | Type | Description |
|-------|------|-------------|
| `id` | UUID | Unique message identifier |
| `conversation_id` | UUID | Parent conversation reference |
| `sender` | TEXT | `"user"` or `"assistant"` |
| `message` | TEXT | Message content (Markdown for AI responses) |
| `created_at` | TIMESTAMP | When the message was sent |

### 5.2 Message Ordering

- Messages displayed in chronological order (oldest first)
- Sorted by `created_at ASC` when loading conversation
- New messages appended at the bottom of the chat

### 5.3 Message Content

| Sender | Content Format |
|--------|---------------|
| **User** | Plain text |
| **Assistant** | Markdown (headings, lists, code blocks, Mermaid diagrams) |

## 6. Search Functionality

### 6.1 Search Scope

| Search In | Method |
|-----------|--------|
| **Conversation titles** | PostgreSQL ILIKE or full-text search |
| **Message content** | PostgreSQL full-text search on messages table |

### 6.2 Search Behavior

| Aspect | Detail |
|--------|--------|
| **Trigger** | User types in search bar |
| **Debounce** | 300ms before API call |
| **Results** | Filtered conversation list updating in real-time |
| **Highlight** | Matching text highlighted in results (optional) |
| **Empty results** | "No conversations found matching '{query}'" |

## 7. Context Management for Continued Chats

When a user continues an old conversation, the RAG pipeline must include prior context:

### 7.1 Context Loading Strategy

| Data | Source | Limit |
|------|--------|-------|
| **Conversation history** | Last N messages from `messages` table | 10 messages |
| **Document chunks** | FAISS retrieval based on current question | Top 5 chunks |
| **Resource scope** | Original resource linked to conversation | Single resource |

### 7.2 Prompt Construction for Continued Chat

```text
System prompt + Retrieved document chunks + Last 10 messages + New user question
```

This ensures the AI understands both the document content and the ongoing conversation thread.

## 8. Conversation Management

### 8.1 Delete Conversation

| Aspect | Detail |
|--------|--------|
| **Who** | Conversation owner only |
| **UI** | Hover → reveal delete icon; confirmation dialog |
| **Backend** | DELETE conversation row + cascade delete all messages |
| **Undo** | Not supported (permanent deletion) |

### 8.2 Rename Conversation

| Aspect | Detail |
|--------|--------|
| **Who** | Conversation owner only |
| **UI** | Hover → reveal edit icon; inline text edit |
| **Backend** | UPDATE conversations.title |
| **Max length** | 100 characters |

### 8.3 Download Conversation

| Aspect | Detail |
|--------|--------|
| **Format** | Markdown (.md) or plain text (.txt) |
| **Content** | All messages with timestamps and sender labels |
| **Trigger** | "Download" button in chat header |

**Export format example:**

```markdown
# Explain normalization in simple words
Date: 2026-07-28

**User:** Explain normalization in simple words.

**AI:** Imagine a school library where the same book details...

**User:** Can you explain 2NF?

**AI:** Second Normal Form (2NF) builds on 1NF by...
```

## 9. Access Control

| Rule | Detail |
|------|--------|
| **View own chats** | Users can only see their own conversations |
| **Unverified users** | Cannot access chat history (blocked by auth module) |
| **Admin access** | Admins cannot view other users' private chats |
| **API validation** | Backend verifies `user_id` matches authenticated user on all chat endpoints |

## 10. API Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| POST | `/conversations` | Create new conversation |
| GET | `/conversations/{user_id}` | List all conversations for a user |

## 11. Database Schema

### 11.1 Table: `conversations`

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | UUID | PRIMARY KEY | Auto-generated |
| `user_id` | UUID | FK → users.id, NOT NULL | Conversation owner |
| `title` | TEXT | NOT NULL | Auto-generated or user-set title |
| `created_at` | TIMESTAMP | DEFAULT now() | Creation timestamp |

### 11.2 Table: `messages`

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | UUID | PRIMARY KEY | Auto-generated |
| `conversation_id` | UUID | FK → conversations.id, NOT NULL | Parent conversation |
| `sender` | TEXT | NOT NULL | `"user"` or `"assistant"` |
| `message` | TEXT | NOT NULL | Message content |
| `created_at` | TIMESTAMP | DEFAULT now() | Message timestamp |

### 11.3 Relationships

```text
users (1) ──── (N) conversations (1) ──── (N) messages
```

- One user has many conversations
- One conversation has many messages
- Deleting a conversation cascades to delete all its messages

See [Module 09 – Database Design](./09-database-design.md) for indexes and constraints.
